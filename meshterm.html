meshTerm 2.2 - User Guide
For iPhone and iPad.

1. Overview

meshTerm is an SSH client for iOS and iPadOS. It connects to remote servers over standard SSH, with built-in Tailscale networking, SFTP, port forwarding, and a fast Metal terminal.

For sessions that outlive a disconnect, meshTerm offers three levels of persistence, chosen per host: tmux (your shell survives on the server using software already on most machines, with tmux windows and panes shown as native panes), mtRoam (the optional open-source mtRoam daemon on your own host, for full persistence that survives network changes, app suspension, device switches, and daemon restarts), and None (a plain SSH shell that ends with the connection). See Persistent sessions for the walkthrough and Halo for how mtRoam's persistent ring buffer works.

Beyond the terminal, meshTerm includes:

  • Multiple concurrent sessions per host, with attach modes for sharing or watching.
  • A predictive-echo overlay that makes typing feel native on slow links.
  • A browseable view of the host's shell history, plus a chip strip of inline suggestions.
  • An SFTP file browser that integrates with the iOS Files app.
  • A customisable macro bar and a searchable Snippet Vault.
  • Native Tailscale integration for keyless SSH on your Tailnet.

3. Getting started

The welcome tour 2.2

On first launch meshTerm shows a short welcome tour: tap Get Started, skim What it does, then answer How do you connect?:

  • Tailscale (Recommended): sign in to your tailnet, then pick a device to add. If your tailnet requires an admin to approve new devices, meshTerm shows Waiting for device approval with an Open Admin Console button; the connection completes by itself once the device is approved.
  • SSH: add a host with a key or password (below).
  • Continue skips this step and goes straight into the app.

Replay the tour any time from Settings > General > Show Welcome Tour.

Adding your first host

  1. On the Sessions tab, tap + in the top right (or the globe icon to browse and add a host from your Tailnet).
  2. Where is it? Fill in the connection details:
    • Label: a friendly name (for example demo).
    • Hostname or IP: the address of your server.
    • Port: defaults to 22.
    • Username: your account on the server.
  3. How do you sign in? Pick an authentication method: password, SSH key, or (if the server runs Tailscale SSH) Tailscale SSH.
  4. Session preferences: pick the host's Persistence: tmux, mtRoam or None (see Choosing persistence). You can change it later in Edit Host > Session.
  5. Ready to connect: check the summary and tap Connect.

Connecting

Tap any host in the list to open a terminal session. On first connect to a new host, meshTerm asks you to verify its host-key fingerprint (see Trusted servers) - tap Trust & Connect to proceed.

4. Managing hosts

Editing a host

Long-press a host card and tap Edit. Edit Host opens on a short list of screens:

  • Connection: address, authentication, tags, operating system, and (for an mtRoam host) the mtRoam transport.
  • Session: the Persistence picker and the settings of the chosen option (see Choosing persistence).
  • Shell & Environment: working directory, the per-host Back-to-prompt button setting, and environment variables.
  • Tunnels: port forwarding rules.

Below them, Changes on this host lists what meshTerm leaves on the server, such as agent notification hooks, and lets you turn them off or remove them where that is possible.

Save is available on every screen, so you can save where you made the change. When Save is disabled, a note at the bottom says why (a host needs a label, hostname and username). A password host with no password saved on this device can still be saved; a reminder asks you to enter the password in Connection before you connect.

Deleting a host

Tap Edit at the top of the Sessions tab, then the red minus on a host to remove it (you can also drag to reorder here). A host is also reachable by long-press for a context menu of actions.

Tags & filter chips

Tag hosts in the editor's Tags section (comma-separated, e.g. prod, web). A chip row at the top of the Sessions tab lets you filter by tag.

Host import / export

Settings → Hosts gives you two buttons:

  • Import from .ssh/config - pick a host you can already SSH to. meshTerm reads its ~/.ssh/config over SSH and shows a checklist of entries to mirror. Imported hosts start in password mode with an empty password - set credentials in the editor before connecting.
  • Export to ssh_config - emits a standard OpenSSH config file you can drop into your dotfiles or AirDrop to a laptop. Roam-enabled hosts are exported as plain SSH (the Roam protocol is meshTerm-specific).

Distro / OS icons

Each host card shows a small icon for its operating system - Ubuntu, Debian, Fedora, CentOS / Rocky / Alma, Arch, openSUSE, NixOS, Linux Mint, Gentoo, elementary OS, Void, Solus, Zorin, deepin, macOS (Apple logo), FreeBSD, Android, AIX, and GNU/Hurd. The icon is tinted with the host's per-card hue. Choose the OS in Edit Host > Connection > Operating System; Unknown falls back to the generic Linux icon and shows the host's initials as a monogram.

5. Connecting to a host

Tap any host in the Sessions tab to open a terminal session.

Verifying the host key

On the first connection to a new host, meshTerm shows its host-key fingerprint and asks you to confirm it (trust on first use). Tap Trust & Connect to save the key and proceed. If a host's key changes later, meshTerm does not fail silently: it shows an accept-or-compare sheet so you can review and re-trust the new key in place.

Reconnecting

meshTerm keeps working as you move between networks and background the app; when you return, live sessions reconnect automatically. A plain SSH shell ends when its connection drops. To keep a shell alive across drops, use tmux or mtRoam (see Persistent sessions).

Sessions on a host

For a host that uses tmux or mtRoam, long-press it and choose Sessions… to see the sessions living on the server. Tap one to attach, tap + to start a new one, or swipe a row to the left and tap End session to close it on the host (meshTerm asks first). Inside a tmux session, windows and panes are managed from the palette's tmux page: see tmux sessions.

6. Persistent sessions: tmux and mtRoam

A plain SSH shell ends when its connection drops. To keep your shell running on the host while your phone sleeps, changes network or switches to another device, meshTerm offers three choices per host:

  • tmux: your shell lives in a tmux session on the host, using software already on most servers. This is the default for new hosts.
  • mtRoam: your shell lives in the open-source mtRoam service (mtroamd) on your own host, with its Halo scrollback buffer, named sessions and attach modes.
  • None: plain SSH. The shell ends with the connection.

Choosing persistence for a host 2.2

Pick one in the Persistence picker (tmux, mtRoam or None). It is on the Session preferences step when you add a host, and under Edit Host > Session afterwards.

  • With tmux chosen you can also set a Session name (optional); leave it blank to use a name derived from your device. The tmux attach setting is described in Control mode or Legacy.
  • With mtRoam chosen the picker reminds you that it "Needs the mtRoam service (mtroamd) on the host." and links the Install guide. The mtRoam settings (Keep alive, Session name, and so on) appear below it.
  • A host marked as Windows always connects over plain SSH: tmux and mtRoam need a Linux or macOS host.

New hosts start with the choice in Settings > Sessions > Persistence for new hosts (tmux or None). mtRoam is always chosen per host. If a host's choice differs from that default, Edit Host > Session offers Reset to app default.

Check persistence 2.2

Not sure what a host has installed? Open the host's Details (long-press the host) and tap Check persistence in the Persistence section. meshTerm runs one read-only command over SSH and shows a row each for tmux and mtroamd: the version and where it was found, Not found, or Unknown if the host could not be reached. Nothing is installed or changed.

  • The tmux row says Control mode: ready. for tmux 3.2 or newer, or that it is too old for control mode (see below).
  • For an mtroamd that meshTerm installed itself (in ~/.local/bin), the mtroamd row carries the Update, Repair, Restart and Uninstall buttons. Any other copy shows "Installed by a package manager." instead, with a link to the install guide.
  • Finding mtroamd never changes the host's setting: pick mtRoam yourself in Edit Host > Session if you want to use it.

tmux sessions 2.2

On a host with tmux 3.2 or newer, meshTerm talks to tmux directly through tmux's own control mode. Instead of drawing a tmux client inside one terminal, meshTerm knows every window and pane and shows each pane as its own native terminal, with its own scrollback. When you come back to the app, it reattaches to the exact session you left, sized to your screen. The status line you configured in tmux on the host is left alone (the old tmux Status Bar setting is gone).

If another device takes the session over, your screen shows Detached from another device with a Reattach button to take it back.

Panes on iPad and iPhone

  • iPad: the panes of the current window are laid out side by side as tmux arranges them. Drag a divider to resize the panes (the size is applied when you let go); double-tap a divider to even them out.
  • iPhone: held upright, you see one pane at a time. When the window has more than one pane, a small row of dots sits in the top-right corner of the terminal (top-left with Left-handed layout on): tap a dot, or swipe across the dots, to switch panes. The pane you leave keeps running, so switching back shows its current output straight away.

Windows and panes from the palette

While a tmux session is attached in control mode, the keyboard palette gains a fourth page, marked with the tmux icon. It lists your Windows and the Panes of the current window:

  • Windows: tap a window to switch to it; tap New window to add one. Each window's ... menu has Rename window and Close window. On iPad the windows show as a row of chips.
  • Panes: a small map of the window's layout; tap a pane to focus it. Below it: Split right, Split down and, with more than one pane, Zoom / Unzoom. The ... menu has Rename pane, Fit to this screen (useful when a desktop client left the session another size) and Close pane.
  • Resize: in a window with several panes (and not zoomed), Wider, Narrower, Taller and Shorter resize the focused pane, and Even out evens the whole window.

Closing a window or pane asks first, since it also closes whatever is running in it.

With a hardware keyboard, control mode adds its own shortcuts; see External keyboards.

Control mode or Legacy

Control mode is on by default. Each tmux host has a tmux attach setting in Edit Host > Session (shown while Persistence is tmux) with two choices:

  • Control mode: recommended. Native panes, the tmux palette page and the iPad splits described above.
  • Legacy: "a plain tmux client, without splits or the window palette", the way meshTerm attached to tmux before 2.2. Use it if control mode misbehaves on a particular host.

A control-mode session picks up a change to this setting the next time it reattaches; a Legacy session switches to control mode when you start a new session.

Older tmux, and hosts without tmux

  • tmux older than 3.2: meshTerm notices and automatically reconnects with the classic tmux attach, so the session still persists. Check persistence explains this on the tmux row. After you upgrade tmux on the host, tap Check persistence so meshTerm tries control mode again on the next connect.
  • No tmux: the session opens as a plain shell with a No session persistence banner. Where meshTerm knows your distro's install command, Install tmux pastes it at your prompt for you to review and run.

mtRoam

mtRoam (Roam in earlier versions of this guide) is meshTerm's own persistent-session service, powered by the open-source mtroamd daemon on your host. Your shell survives reconnects, app suspension, device switches, and even daemon restarts, with full scrollback replayed on reattach. Its signature is Halo, the persistent ring buffer described below.

Installing mtroamd

Installing mtroamd from the app is deprecated from iOS 2.2. meshTerm no longer installs the daemon. Install it with your server's package manager (apt, dnf, apk, AUR or Nix) or build it from source, following the mtroamd install page. A copy the app installed earlier (in ~/.local/bin) keeps working, and the app still offers Update, Repair, Restart and Uninstall for it. To move that copy onto a package, see Switching from the app-installed mtroamd to a package.

The install page is the place for the repository and signing-key setup of each package manager. Once the repository is added, the install itself is one line:

SystemInstall
Debian, Ubuntu (apt)sudo apt install mtroamd
Fedora (dnf)sudo dnf install mtroamd
Alpine (apk, x86_64 for now)apk add mtroamd (as root, after adding the repository)
Arch (AUR)mtroamd-bin (prebuilt) or mtroamd (builds from source)
Nix / NixOSThe flake's NixOS module or home-manager module (see Nix below)
Any systemd LinuxBuild from source

The packages come in two channels. Stable is the one the App Store version of meshTerm pairs with, and the one to use. Dev carries pre-releases that pair with TestFlight builds.

On apt and dnf, run the install as your normal login user with sudo: the package then starts mtroamd for that user and keeps it running after you log out. Check it with mtroamd doctor. Then set the host's Persistence to mtRoam in Edit Host > Session and connect.

Updating and maintaining mtroamd

  • Package-managed copy: update it with the package manager, for example sudo apt upgrade mtroamd or sudo dnf upgrade mtroamd. The app shows "Installed by a package manager." in place of the maintenance buttons, adding "Update it with your package manager." when a newer daemon is available.
  • App-installed copy (in ~/.local/bin): when meshTerm needs a newer daemon, the host shows mtRoam service update available with the installed and available versions; tap Update now. The host's Details screen also offers Repair (re-downloads the current release, verifies it and restarts), Restart mtRoam service and Uninstall. Each asks first. Sessions set to persist across restarts are kept through a Repair or Restart; Uninstall ends all mtRoam sessions on the host. Your pairing (certificate and key) is kept either way.
  • If meshTerm has never seen the daemon's version, or does not yet know who installed it, it asks you to run Check persistence before it offers any of these.
Before 2.2, connecting to a Roam host without the daemon opened a Set Up Roam sheet that downloaded and installed mtroamd. That sheet, and the Reinstall button, are gone.

Building from source

On any systemd Linux you can build mtroamd yourself. You need Go 1.26 or newer. Build a release tag (the version shown as "Current stable" on the install page), not an arbitrary development commit: the app requires a minimum daemon version.

git clone https://github.com/AG-Studio-Apps/mtroamd.git
cd mtroamd
git checkout v1.8.0          # use the current stable tag from the install page
make build build-mtroam      # builds ./mtroamd and ./mtroam
sudo install -m 755 mtroamd mtroam /usr/local/bin/

If this host has an app-installed copy, switch it over with /usr/local/bin/mtroamd migrate (see AUR and source builds). Otherwise set up the service yourself:

mkdir -p ~/.config/systemd/user
mtroamd unit print --bin=/usr/local/bin/mtroamd > ~/.config/systemd/user/mtroamd.service
systemctl --user daemon-reload
systemctl --user enable --now mtroamd
sudo loginctl enable-linger "$USER"
mtroamd doctor
Install your build to /usr/local/bin, not ~/.local/bin. A binary in ~/.local/bin is treated as the app-installed copy: the app offers Update, Repair and Uninstall for it, and an update would replace your build with a release download.

To update a source build, check out the new tag, rebuild, install, and restart (a restart keeps live sessions):

git pull && git checkout <new tag>
make build build-mtroam
sudo install -m 755 mtroamd mtroam /usr/local/bin/
systemctl --user restart mtroamd

Switching from the app-installed mtroamd to a package 2.2

If meshTerm installed mtroamd on a host for you (it lives at ~/.local/bin/mtroamd), you can move that host onto a package or a source build. Whatever the method, the daemon's state in ~/.local/share/mtroamd (the certificate the app trusts, and your session state) is kept, so the app reconnects with no re-pairing. There is nothing to change in the app: it finds the new binary on its next connect and dials the same socket (~/.local/share/mtroamd/mtroamd.sock), which every package uses by default.

apt and dnf: automatic

  1. Add the repository from the install page.
  2. As your normal login user, run sudo apt install mtroamd or sudo dnf install mtroamd.
  3. Watch for mtroamd: migrating existing ~/.local/bin install for '<you>' followed by a line saying it migrated with sessions preserved. That's it.

What happens. The package notices the ~/.local/bin copy belonging to the user who ran sudo and runs mtroamd migrate --yes as that user. migrate:

  • rewrites your systemd user service to run /usr/bin/mtroamd, keeping the same ports and socket;
  • restarts the daemon in a way that keeps your live sessions running (they reattach to the new daemon);
  • removes ~/.local/bin/mtroamd only once the new daemon is confirmed running;
  • puts your previous setup back if any step fails, so you are never left half-migrated.

If it didn't migrate. If the installer printed that the user session "isn't reachable from here" or that the auto-migration failed, or you installed as root or from automation (no sudo user), run the migration yourself as your login user:

/usr/bin/mtroamd migrate

Use the full path: until the migration runs, a plain mtroamd may still find the old copy in ~/.local/bin first, which only replies that there is nothing to migrate to. Until you migrate, both copies exist and the old one keeps running, so package upgrades do not take effect.

Several users on one host? Only the user who ran sudo is migrated. Each other user with an app-installed copy runs /usr/bin/mtroamd migrate themselves.

AUR and source builds: run migrate once

These do not migrate automatically. After installing, run migrate as your login user, using the new binary's full path (the old ~/.local/bin copy refuses with "nothing to migrate to"):

/usr/bin/mtroamd migrate          # AUR
/usr/local/bin/mtroamd migrate    # source build
sudo loginctl enable-linger "$USER"   # if not already, so it survives logout and reboot

migrate performs the same safe switch described above: same ports and socket, live sessions kept, the old binary removed only once the new daemon is running, and a rollback if anything fails.

Nix and NixOS

Don't use mtroamd migrate here (it would write a Nix store path into your own service file). Instead, remove the app-installed copy while keeping its state, then let Nix run the daemon:

  1. As your login user: 
    ~/.local/bin/mtroamd uninstall --yes
    This stops the old daemon and removes its user service, ~/.local/bin/mtroamd and ~/.local/bin/mtroam, and keeps ~/.local/share/mtroamd. Never add --purge: that deletes the certificate, and the app would have to trust the host again.
  2. Enable the module and rebuild. On NixOS: 
    imports = [ mtroamd.nixosModules.default ];
services.mtroamd = { enable = true; users = [ "you" ]; };
    This also keeps the daemon running after you log out and puts mtroamd on your PATH. With home-manager, set services.mtroamd.enable = true; and, in your NixOS configuration, users.users.<you>.linger = true.
Open mtRoam sessions on the host end when the old daemon stops. Save your work first.

Alpine (apk)

Alpine has no systemd, so there is no migrate step:

  1. As your login user: ~/.local/bin/mtroamd uninstall --yes (keeps your state; never add --purge).
  2. As root, install mtroamd from the apk repository on the install page.
  3. In /etc/conf.d/mtroamd, set MTROAMD_USER to your login user. The daemon starts your shells as that user and uses that user's ~/.local/share/mtroamd, so the certificate the app trusts carries over.
  4. Start it, and enable it at boot: rc-update add mtroamd && rc-service mtroamd start.

As with Nix, open sessions end when the old daemon stops.

Verify

  • mtroamd doctor reports the daemon's health.
  • command -v mtroamd should print the package or source path, not ~/.local/bin. (Open a new shell first if it still shows the old path.)
  • On systemd: systemctl --user status mtroamd. On Alpine: rc-service mtroamd status.
  • In meshTerm, open the host's Details and tap Check persistence. The mtroamd row now shows the new path and "Installed by a package manager." in place of Update, Repair, Restart and Uninstall. (meshTerm also re-checks by itself when you open the host's Details and its last check is more than a day old.) From now on, update with your package manager, or by rebuilding for a source install.

The app-installed companion CLI ~/.local/bin/mtroam is left in place by migrate; you can delete it so the packaged mtroam is used instead.

Choosing a transport (Direct vs SSH Tunnel)

mtRoam can reach the daemon two ways. With Persistence set to mtRoam, open Edit Host > Connection, then mtRoam transport > Transport Details > mtRoam Transport:

  • Direct (QUIC/TCP): meshTerm dials the daemon's QUIC port directly over UDP. Lowest latency, but the daemon's UDP port (49820 by default) has to be reachable from your device. The Firewall setup row under Transport Details opens the exact firewall rules for the host.
  • SSH Tunnel: the mtRoam protocol is carried inside the SSH connection you already authenticated with. Nothing extra to open: it works through any firewall that allows SSH, at a little more latency than Direct.

If you choose Direct and the UDP port turns out to be blocked, meshTerm falls back to the SSH tunnel for that connection, so a session always comes up. Over meshTerm's built-in Tailscale, Direct uses mtRoam over TCP on the tailnet instead (port 49920 by default), and Firewall setup shows the matching rule.

Multiple named sessions per host

Each mtRoam host can hold any number of named sessions: dev, logs, tests, whatever you want. Tap the host and a picker appears showing the existing sessions; tap one to attach, or tap + to start a fresh one.

Manage sessions from the picker:

  • Rename: swipe a row to the right, or long-press it and choose Rename…. Only the label changes; the shell and its scrollback are untouched.
  • End session: swipe a row to the left, or long-press it. Confirmation required.
  • Open read-only: long-press a row to watch a session without taking it over (see Attach modes).

If a host only has one session, meshTerm skips the picker and attaches directly. If it has none, a fresh session is spawned and you connect to it.

Halo: the persistent ring buffer

The thing that makes Roam durable is a per-session ring buffer the daemon keeps for every session. We call it Halo. It is a rolling window of your session's output (up to 4 MiB per session) that lives on the host, independent of whether any client is attached. When your phone drops off, backgrounds, or switches networks, the shell keeps running and its output keeps flowing into the ring, so nothing is lost while you are away.

When you reattach, the daemon replays the ring from the exact byte you last acknowledged and then hands you straight into the live stream with no visible seam. Because the buffer tracks output by byte position, replay resumes precisely where you left off rather than redrawing the whole screen. A few details worth knowing:

  • Recency window. meshTerm asks for only as much replay as your scrollback setting can actually display, so a quick reconnect does not re-stream megabytes you will never scroll back to.
  • Full-screen apps. Inside a full-screen TUI (vim, htop, a pager) the replay budget tightens automatically, since an alt-screen app has no scrollback of its own. The daemon also reconstructs the app's stable bottom rows (status bars, prompts) so they are intact the moment you reattach.
  • Honest truncation. If you were away long enough that the oldest output rolled out of the 4 MiB ring, meshTerm tells you plainly that some output was lost during the disconnect rather than pretending the scrollback is complete.
  • Survives daemon restarts. With Persist across mtRoam service restarts on, the ring is checkpointed to disk, so your scrollback and session come back even after a self-update or a host reboot.

Halo lives entirely on the open-source daemon; nothing about your session travels anywhere but between your device and your own host. The full buffer and replay design is documented in the mtroamd repository.

Default session and pinning

In Edit Host > Session, the mtRoam section (shown while Persistence is mtRoam) holds:

  • Session name: which named session the host opens by default. Tap it to change the session or remove sessions you no longer need. None uses your most recently attached one.
  • Always open this session: pins the host directly to that session, skipping the picker. The picker is still available via long-press > Sessions….
  • Persist across mtRoam service restarts: when on, the session's scrollback is snapshotted to disk so it survives a daemon restart (for example after an update or a host reboot).

Keep-alive (idle timeout)

Keep alive, in the same section, sets how long the mtRoam service holds a session when no client is attached. Options: Default (30 days), 1 hour, 1 day, 7 days, 30 days, or Never (until daemon restart).

Attach modes

When you join a Roam session, meshTerm uses one of three roles:

  • Exclusive (default) - you receive output, you send keystrokes, you own the terminal size. If someone else attaches exclusively, you're handed off to read-only.
  • Read-only - you see everything but your keystrokes are dropped at the daemon. Useful for watching a colleague drive, or for a second device tailing along.
  • Passive - a quiet tail. Same as read-only but invisible to the other clients' "who else is attached" indicators. Used by the mtroam tail command.

Any number of read-only watchers can coexist with a single exclusive driver. The session label in the bar shows your role.

To watch rather than drive, long-press a session in the picker and choose Open read-only. When another device holds the session, your screen shows a Live on another device banner: tap Take control to move typing to this device, and the other device becomes the viewer.

Desktop CLI: mtroam 2.0

The mtRoam daemon ships with a small companion command-line tool called mtroam, installed alongside mtroamd by the packages and by a source build. Use it from any SSH session on the host (or from a laptop with ssh user@host mtroam …) to manage sessions without opening the iOS app.

Subcommands:

  • mtroam list - enumerate sessions on this host (id, name, idle time, attached clients).
  • mtroam session-info <name> - detail for one session, including geometry and idle state.
  • mtroam status - daemon health snapshot.
  • mtroam search <regex> <session> - grep a session's scrollback.
  • mtroam doctor - diagnostic checks for daemon, supervisor unit, and lingering.
  • mtroam tail <session> - passively attach to live output. No input, no replay; just a tail.
  • mtroam new --name <name> - create a new named session without attaching to it. Useful for pre-creating a session before opening the app, or for cron jobs.
  • mtroam attach <session> - attach to a session as the local terminal. Detach with ~. on a fresh line.
  • mtroam kill <session> - reap a session.
  • mtroam rename <session> <new-name> - rename a session. Buffer and active attaches are unaffected.
  • mtroam update - check for and apply a signed self-update from the project's GitHub Releases.
  • mtroam restart - cycle the daemon via its supervisor. In-flight sessions survive the restart.
  • mtroam uninstall - remove the mtroam binary.

On a host where mtroamd came from a package manager, update and remove it with the package manager instead (see Installing mtroamd).

Authentication uses your normal SSH config - ~/.ssh/config, ssh-agent and keys all work. mtroam invokes the system ssh binary, so anything that works for ssh user@host works here too.

Each mtroam invocation accepts --host user@host to pick a target, or reads $MTROAM_HOST, or falls back to ~/.config/mtroam/host.

7. Agent Mode 2.1

Agent Mode runs a coding agent on one of your own hosts and gives you a native chat to drive it from. Start Claude Code, Codex, or Gemini on any host, and instead of watching a raw TUI scroll past, you get a real conversation: streaming replies, tappable approvals, and the agent's tools, all inside meshTerm's own interface.

The agent runs where your code is. meshTerm launches the provider's own CLI on the server, over the same SSH or mtRoam connection you already use, so the model works against your real files, your real environment, and your own API keys or logins on the host. Nothing about your project leaves your host and your device.

Starting an agent

Open the keyboard palette's features page and tap Agents, or start one from a running session. Pick a provider and meshTerm opens the agent chat. From there you type as you would in any chat: your message goes to the agent, and its reply streams back token by token.

Replies, models, and effort

  • Streaming replies - text appears as the model produces it, so you can read along and stop early if it is heading the wrong way.
  • Model picker - choose which model the provider should use for this conversation.
  • Thinking-effort picker - dial how much reasoning the model spends before it answers, where the provider supports it.
  • Token-usage chips - each turn shows what it cost in tokens (or an estimate where the provider does not report exact counts), so a long session never surprises you.
  • Slash commands - the provider's own slash commands work straight from the chat input.

Plan mode

Turn on plan mode and the agent works out an approach and lays out the steps before it touches anything. Review the plan, then let it proceed. It is the safe way to point an agent at a change without it editing files the moment you hit send.

Approvals and sandboxing

Agents ask before they act, and the request waits for you instead of scrolling away:

  • Codex and Claude ask before running a command or editing a file. The approval request appears as a pill in the chat and stays pinned until you answer it, so a prompt never gets lost in a fast-moving conversation. Approve or deny with a tap.
  • Gemini Sandbox pauses any write outside the working directory and surfaces it for your approval, so the agent can read freely but cannot change files elsewhere without a yes from you. On hosts that support it, an optional bubblewrap layer adds kernel-level hardening around the agent's process.

File attachments

Attach files straight from iOS into the agent's workspace. Pick from the iOS Files sheet and meshTerm places them where the agent can see them, so you can hand the model a log, a screenshot, or a document without leaving the chat.

Persistence and resume

Agent sessions are as durable as the rest of Roam. An agent keeps running through an app restart or a network drop and picks straight back up when you return. You can resume any previous conversation, including agent sessions you started from the terminal rather than the chat, so a session you kicked off in a plain shell is still yours to continue in the native chat later.

Notifications 2.1.11

meshTerm can push you a notification the moment an agent needs you, even while the app is in the background or fully closed. You get a needs-approval alert when Claude Code or Codex pauses for a permission decision, and a turn finished alert when an agent completes a turn and is waiting for your next instruction. Tap the notification and meshTerm opens the exact session it came from, dropping you straight back into that conversation.

Notifications are opt in per host, on each device. In Edit Host, turn on Notify this iPhone (Notify this iPad on an iPad). Each of your devices has its own setting: it doesn't sync with your hosts, so turning it on for a host on your iPhone leaves your iPad as it was. The first time an agent starts there, meshTerm installs a small notify hook into that agent's own configuration (Claude, Codex, or Gemini) so the host can signal your device; an agent already running when you opt in starts notifying once you relaunch it. The hook holds no relay key: each device keeps its own in a private file on the host that only your user can read. In Settings > Agents > Notifications you choose whether approvals, turn-completions, or both reach you, and those switches apply immediately, even to sessions already running.

Alerts come through Apple Push Notification service (APNs) via our relay, over encrypted connections. They carry no information that identifies you, your hosts or your work: no prompts, commands, code, file names, or host or session names, just an anonymous tag, the kind of alert and the agent's name. Your device adds the session name itself. Notifications work for agents you run in the terminal (over tmux or mtRoam) as well as in the native chat, covering Claude Code and Codex for both approvals and turn-completion, and Gemini for turn-completion.

Notifications follow you. Alerts from a terminal session go to the device you used it on most recently, if that device has notifications on, and keep going there while it's locked. Agent chat alerts go to the device that sent the message, and herdr alerts go to every device that has herdr alerts on. A device that has notifications off never changes where your other devices' alerts go, and turning them off on a device removes it from the host straight away, even for an agent that's already running.

herdr 2.2

herdr is an open-source terminal workspace for coding agents. It keeps Claude Code, Codex, Gemini and other agents running in panes on your host, whether or not meshTerm is open, and knows when one is waiting for you. meshTerm reads herdr's own status over SSH, so you can see and answer your agents from your phone without opening a terminal.

Free on your host. The free plan includes one herdr session at a time, on top of your one live session, with no limit on the agents, tabs and workspaces inside it. meshTerm Pro adds more hosts and parallel sessions.

Set Up herdr

Open Set Up herdr from the Agents tab (the onboarding card, or + on the herdr side) or from Settings > herdr. Pick a host and meshTerm checks it: whether herdr is installed and which version, whether python3 is there for live status, and whether alerts are on. If herdr is missing or older than 0.9.2, Install runs herdr's official installer on the host and shows you its output as it goes. The exact command is shown before it runs:

curl -fsSL https://herdr.dev/install.sh -o ~/.mt-install-herdr.sh && sh ~/.mt-install-herdr.sh && rm -f ~/.mt-install-herdr.sh

It downloads first so a failed download can't look like a success, puts one program in ~/.local/bin, needs no admin rights and changes nothing else. Prefer Homebrew, mise or Nix? Follow herdr's install guide instead. The last step turns on alerts for the host and starts your first herdr session.

The Agents tab: Chats and herdr

Once herdr is found on a host, the Agents tab has two sides. Chats are the agents meshTerm runs for you in its native chat. herdr is an overview of every herdr session on every host: what needs you first, then each host's sessions as cards with their agents and status. A slim banner tells you when the other side has something waiting, and the tab's badge counts both. Pull down to check your hosts again.

Tap a session card to open its dashboard: workspaces, tabs and panes, which agent is working, waiting or done, and buttons to open the terminal, add a tab or a workspace. From the dashboard's menu you can pin, end or delete a session. A herdr session's terminal is an ordinary terminal session in meshTerm.

Alerts and approvals

Turn on Notify for herdr Agents for the host, in Set Up herdr or in Changes on this host (it needs Notify this iPhone or Notify this iPad on first), and the agents herdr recognizes, Claude, Codex and Gemini included, alert you when they need you or finish (see Notifications). It adds a small notification plugin to herdr, and every device that turns it on gets herdr's alerts. Alerts come through Apple Push Notification service (APNs) via our relay, over encrypted connections, and carry nothing that identifies you, your hosts or your work. When an agent waits for approval, Review shows the full prompt and lets you approve or deny it from your phone; anything meshTerm can't read safely opens the terminal at that pane instead.

herdr in the terminal

In a herdr terminal the keyboard palette has a herdr page that sends herdr's own keys under your host's prefix: new and next tab, splits, zoom, focus moves, workspaces and detach. Settings > herdr > herdr Shortcuts lists them all.

Background checks

meshTerm checks each host for herdr once, then once a day on hosts that have it, when you open Agents or Settings > herdr. It only checks hosts whose host key you've already trusted, at most three at a time, and backs off for a week after a sign-in failure. Turn Look for herdr on my hosts off in Settings > herdr to stop all background checks; pull-to-refresh and Set Up herdr still check when you ask.

Password

9. SSH keys

Manage keys in Settings → Hosts & Network → SSH Keys.

Supported key types

  • Ed25519 (recommended default).
  • ECDSA on NIST curves P-256, P-384, P-521.

RSA keys aren't supported in 2.0; the importer will tell you if you paste one.

Generating a new key

  1. Settings → Hosts & Network → Add Key.
  2. Pick a type and enter a label (e.g. "Work iPhone").
  3. Tap Generate. meshTerm creates the key pair, saves the private half in the iOS Keychain, and shows the public key in OpenSSH format.
  4. If you have saved hosts, an Install on a Host section appears immediately. Pick a host, tap Install Key, and meshTerm appends the public key to ~/.ssh/authorized_keys on that server.
Install on a Host uses strict host-key verification. If you haven't already trusted the target host, the section asks you to connect via the terminal first to accept the fingerprint, then return and install.

Importing an existing key

  1. Settings → Hosts & Network → Add Key → Import.
  2. Paste the full OpenSSH-format private key (including the BEGIN and END lines).
  3. If the key is passphrase-protected, enter the passphrase. meshTerm decrypts it on import and stores the seed in the Keychain - there's no second prompt at connect time.
  4. Tap Import.

Copying a public key

Tap the copy icon next to a key to copy the OpenSSH public key to your clipboard. Paste it into ~/.ssh/authorized_keys on any server you want passwordless access to.

Deleting a key

Swipe a key left and tap Delete. The private key is permanently removed from the Keychain. Hosts using that key will fail to authenticate until you reassign one.

Where keys live

  • Private keys are stored in the iOS Keychain. By default they are marked WhenUnlockedThisDeviceOnly, so they stay on this device and never reach iCloud. If you turn on iCloud Sync (Settings; off by default; a Pro feature), your secrets migrate to iCloud Keychain, which is end-to-end encrypted, so they become available on your other devices. Tailscale credentials never sync.
  • Public keys are stored alongside the host record for display purposes.

10. Tailscale

meshTerm has a built-in Tailscale networking stack, so no separate Tailscale app is required. Add your Tailnet credentials and meshTerm connects to your devices directly over WireGuard. SSH, SFTP, Roam, and all auxiliary connections route through the encrypted Tailscale tunnel natively.

Routing modes

Each host uses one of two routing modes. Set the default in Settings → Hosts & Network → Tailscale, and override it per host in Edit Host:

  • Built-in (Tailscale) - meshTerm's own in-process Tailscale node. Works alongside any system VPN and needs a Tailscale profile. This is the recommended default, and it does not depend on the Tailscale app being installed.
  • Device network - uses your device's normal networking: it routes via the Tailscale app if that app is running, or connects directly otherwise.

Setting up Tailscale 2.0.2

  1. Tap the globe icon in the host list (or go to Settings → Hosts & Network → Tailscale) and create a profile.
  2. Tap Sign in with Tailscale - a browser sheet opens and you sign in with your Tailscale account (Google, Microsoft, GitHub, Apple…). No keys to generate, nothing to renew. If your tailnet requires device approval, meshTerm waits and connects the moment an admin approves.
  3. That's it. Tap the globe icon to browse your Tailnet and add devices in a tap - once connected, the device list comes straight from your tailnet, no API token required.

Prefer not to sign in through a browser? An auth key works exactly as before. And an optional read-only API token supplements discovery: it lets meshTerm list your devices even when it isn't connected to the tailnet (or when you route through the Tailscale app in Device network mode).

The embedded Tailscale node starts automatically when you open the app. You can see its status (connected, IP addresses, signed-in identity) in Settings → Hosts & Network → Tailscale.

Tailscale SSH

Devices on your Tailnet with Tailscale SSH enabled connect without passwords or keys - Tailscale authenticates the connection at the network layer using your device's identity. Set the host's authentication method to Tailscale SSH in the host editor.

Auth keys (alternative to sign-in)

If you'd rather not authenticate through a browser - or you're automating setup - the embedded node can join your Tailnet with a Tailscale auth key instead. Generate one at login.tailscale.com → Settings → Keys:

  1. Click Generate auth key.
  2. Enable Reusable so the key survives app restarts.
  3. Optionally enable Ephemeral so the node auto-removes from your Tailnet when meshTerm isn't running.
  4. Copy the key and paste it into Settings → Hosts & Network → Tailscale → Auth Key in meshTerm.

The auth key is stored in the iOS Keychain. meshTerm uses it to join your Tailnet on each launch - no browser login required. Auth-key profiles browse the device list exactly like signed-in ones: connected = no API token needed.

Multiple Tailscale profiles 2.0

meshTerm can hold more than one Tailscale identity - for example a work tailnet and a personal one, or a separate profile per client. Manage them in Settings → Hosts & Network → Tailscale, where each profile carries its own sign-in (or auth key) and optional read-only API token.

  • Add a profile - tap New Tailscale Profile, name it, and sign in with your Tailscale account (or paste an auth key).
  • Switch profiles - open a profile and tap Connect. Only one profile's node is up at a time, so switching brings the previous one down and the chosen one up. The device browser also offers Connect / Disconnect / switch directly, and warns you first if switching would drop live sessions.
  • Browse per tailnet - the device browser shows whichever profile you pick. The connected profile lists devices straight from its tailnet; browsing a profile that isn't connected uses its read-only API token.

Binding a host to a profile

In the host editor you can bind a host to a specific Tailscale profile. When you open that host, meshTerm switches to its bound profile first - so a work host always comes up on the work tailnet and a personal host on the personal one, with no manual switching. Hosts left unbound use whichever profile is the current default.

11. Port forwarding & Tunnels

meshTerm can forward network ports over an SSH connection, the same way ssh -L and ssh -D do on a desktop. Rules are configured per host and managed from the Tunnels screen.

Rule types

  • Local (-L) - binds 127.0.0.1:<port> on your device and forwards each connection to a host:port reachable from the server. Good for reaching a database, an admin panel, or an internal web app that only listens on the server's own network.
  • Dynamic (-D) - runs a SOCKS5 proxy on 127.0.0.1:<port>; point an app at it and its traffic routes out through the host. Remote (-R) forwarding is not supported yet.

Setting up a rule

In Edit Host → Tunnels → Port Forwarding, tap Add Port Forward, choose Local or Dynamic, and set the local port (and, for Local, the destination as seen from the host). Add a label if you like, then toggle it on.

Managing tunnels

Open Tunnels from a host's long-press menu or the terminal's more-menu. Each rule shows a live status: Listening, Not running, or an error. Tunnels start when the session connects.

For a local web forward, tap its row to open the target in meshTerm's built-in browser; the tunnel stays connected while you browse. For a SOCKS proxy, point an app at 127.0.0.1:<port>.

Tunnels are plain-SSH only (not available over the mtRoam/Halo transport), bind loopback only (reachable just by apps on this device), and are active only while the session is connected and the app is in the foreground. Rules are saved per host and travel with iCloud Sync.

13. Predictions & history 2.0

Predictive echo overlay

When you're typing at a shell prompt, meshTerm mirrors your keystrokes on screen immediately and then reconciles them with the echo that comes back from the server. On a slow link, typing feels native - you see the letters appear as you type, not after a 200 ms round-trip.

The overlay arms itself when meshTerm sees a shell prompt (recognised by the trailing prompt character: $, #, >, or %) and disarms when an alt-screen TUI like vim, htop, or less takes the screen. On Roam hosts, the daemon also reports the live state of the shell's echo flag so meshTerm knows authoritatively whether predictions are safe.

If a prediction doesn't match what the shell actually echoed, the overlay rolls back automatically - you'll see a brief flicker as the mirrored characters are erased and the real ones drawn.

History browse

Pull up the keyboard's history panel to see the host's recent shell history in a sheet. Search across commands and tap one to send it to the active session - the panel closes and the command runs.

The history is fetched live from the host's own ~/.bash_history or ~/.zsh_history over the SSH connection. Nothing is stored locally; what you see is what the shell actually ran.

Prediction chip strip

As you type, a strip of matching commands from the host's shell history appears above the keyboard. Tap a chip to commit the rest of that command without finishing the keystrokes. The chip strip is purely a fast path on top of the history sheet - it doesn't surface snippets, macros, or anything else.

16. Secret Profiles 2.1

Secret Profiles are a meshTerm Pro feature. Creating and using them requires an active Pro subscription.

A Secret Profile bundles a set of environment variables and keys under one name, so you can hand a whole environment to a session at once. Tap to inject a profile into the session you are already in: its variables and keys reach the running shell invisibly, with nothing typed into the terminal and nothing left on screen afterward. Injection works over plain SSH, mtRoam, and tmux.

When injected values take effect

Injection delivers the values to the shell, which picks them up at its next prompt. That means they apply to the next command you run, not to a command already in progress. Inject only updates a pane sitting at a shell prompt; a full-screen app or an agent in the foreground is skipped.

A running agent has an important limitation: Claude Code, Codex, and Gemini keep the environment they launched with, because a running process's environment cannot be changed from the outside, and injection only lands at a shell prompt. For that reason the Apply to this session button is disabled while an agent is in the foreground. To give an agent new secrets: return to a shell prompt, tap Apply to this session there, then restart or resume the agent session, which relaunches it with the new values already in place so it reads them on start. New sessions always receive the secrets on connect, so this only affects an agent that was already live when you injected.

Like secret snippets and macros, profile values are backed by the iOS Keychain and can be gated by Face ID, Touch ID, or your device passcode. Profiles are handy for giving an agent or a shell its API keys and tokens without those values ever landing in your scrollback.

Manage profiles in Settings → Hosts & Network → Secret Profiles, or open the Secret Profiles tile on the keyboard palette's Features page.

18. SFTP file browser

The SFTP browser moves files on and off your servers without leaving meshTerm. It runs over the same SSH transport as your terminal sessions - no additional credentials, no third-party cloud.

  1. From the host detail screen, tap Browse files.
  2. meshTerm opens an SFTP channel over the existing SSH connection and shows the home directory.

  • Tap a folder to enter it; tap Back in the navigation bar to go up.
  • Pull down to refresh.
  • The current path is shown in the title bar.

  1. Tap a file to download. A progress indicator shows bytes transferred.
  2. When the download completes, the iOS Files share sheet appears - pick iCloud Drive, On My iPhone, or any Files-compatible provider.

Uploading

  1. Tap Upload File in the browser toolbar.
  2. Pick one or more files from the iOS Files sheet.
  3. meshTerm uploads them to the current remote directory.

File names are cleaned on upload 2.2. meshTerm keeps your name as it is (spaces, accents and leading dots included, so a .bashrc stays a dotfile) but removes what breaks paths or common tools:

  • a leading cid:, the prefix Mail gives attachments you share into the app;
  • / and \ (path separators), : (which scp and rsync read as a host name), and control characters;
  • < > " | ? *, which Windows OpenSSH servers reject in file names.

The cid: prefix is dropped, each of the characters becomes an underscore, and leading or trailing spaces are trimmed. A name left empty (or just . or ..) falls back to a timestamped name such as file-20261001-142530.

File operations

Long-press a file or folder for options:

  • Rename - enter a new name.
  • Delete - confirm and the file or folder is removed. Non-empty folders aren't deleted in one pass - empty them first.
  • New Folder (toolbar) - create a directory in the current path.

21. Security & App Lock

Trusted servers (TOFU)

meshTerm uses Trust On First Use for host-key verification. The first time you connect to a host, the app shows the server's host-key fingerprint and asks you to confirm. Subsequent connects check the fingerprint silently. If it changes (server rebuilt, key rotated, or something more sinister), the connection is blocked with a warning.

Manage trusted fingerprints in Settings → Hosts & Network → Trusted servers. Swipe an entry left to delete it. If a server's key legitimately changed, delete the old entry and reconnect to accept the new fingerprint.

App Lock

Settings → Privacy & Security → App Lock requires Face ID, Touch ID, or your device passcode to reopen meshTerm. Pick one of:

  • Off
  • Immediately - lock the moment the app backgrounds.
  • After 30 seconds / 1 minute / 5 minutes - short app switches pass through.

Cold launch always requires unlock if App Lock is on.

App Lock requires a device passcode to be set. If you haven't set one, iOS will ask you to in Settings → Face ID & Passcode first.

Credential storage

Everything sensitive lives in the iOS Keychain:

  • SSH private keys (Ed25519, ECDSA).
  • SSH passwords.
  • Tailscale API tokens.
  • Secret snippets and secret macros.

By default nothing sensitive is written to UserDefaults, the filesystem, or an iCloud device backup in plaintext. If you enable iCloud Sync, secrets sync only through iCloud Keychain, which is end-to-end encrypted.

22. iCloud Sync

iCloud Sync keeps meshTerm consistent across your iPhone and iPad. It is opt-in and off by default - turn it on in Settings → iCloud Sync - and it is a Pro feature.

What syncs

  • Your hosts, host tags, and known-host trust (the fingerprints you have accepted).
  • Your SSH key list, macros, snippets, and Tailscale profile names.
  • Appearance and terminal preferences. Some are kept per device class, so an iPhone and an iPad can differ where that makes sense.

Secrets

Sensitive material - SSH private keys, passwords, and secret snippets and macros - is never placed in the synced records. It rides iCloud Keychain instead, which is end-to-end encrypted, so it reaches your other devices without ever being exposed to iCloud in plaintext. Tailscale credentials (auth keys and API tokens) never sync; each device signs in for itself.

Turning it off

Turning sync off stops further propagation but never deletes anything already on a device. To remove synced data, use the erase options under Settings → Privacy & Security.

25. Troubleshooting

Connection

"Could not resolve [hostname]"

  • Check the hostname is spelled correctly.
  • Check your device has a working internet connection.
  • If using a local hostname (e.g. home-server.local), ensure you're on the same network.

"Could not connect"

  • Verify the server is reachable and SSH is running (default port 22).
  • If you're on a local network address, grant meshTerm Local Network permission in iOS Settings → Privacy & Security.
  • Firewalls and NATs can drop idle SSH; set ClientAliveInterval on the server if drops are frequent.

Connection hangs at "Connecting…"

  • Check your network.
  • If connecting via Tailscale, ensure the Tailscale app is open and connected.
  • Try toggling Tailscale off and on.

Authentication

SSH key auth fails silently

  • Confirm the public key is in ~/.ssh/authorized_keys on the server.
  • The ~/.ssh directory needs permissions 700 and ~/.ssh/authorized_keys needs 600.
  • Check sshd_config on the server has PubkeyAuthentication yes.

"Unsupported key type"

meshTerm 2.1 accepts Ed25519 and ECDSA (P-256, P-384, P-521). RSA keys aren't supported. Generate a new Ed25519 key in the app, or convert: ssh-keygen -t ed25519.

tmux

"No session persistence": tmux isn't installed

The host is set to tmux but has no tmux, so the session is a plain shell that ends with the connection. Tap Install tmux on the banner to paste your distro's install command at the prompt, review it, and press Return. Or install tmux yourself, or set the host's Persistence to None to stop the banner.

tmux is too old for control mode

Control mode needs tmux 3.2 or newer. With an older tmux, meshTerm reconnects with the classic tmux attach by itself, so the session still persists, just without native panes and the tmux palette page. Check persistence on the host's Details says so on the tmux row. A newer tmux usually comes from your distro's backports or EPEL, or a static build. After upgrading, tap Check persistence so meshTerm tries control mode again on the next connect.

Control mode misbehaves on one host

Set Edit Host > Session > tmux attach to Legacy. That host then uses a plain tmux client, as before 2.2, while your other hosts keep control mode. Switch back to Control mode any time.

mtRoam

"mtRoam isn't installed on this host."

The host's Persistence is mtRoam, but mtroamd isn't on the host. meshTerm connects through tmux instead and says "mtRoam isn't installed on this host. Using tmux." Tap Switch to tmux to make tmux the host's setting for good, or Install guide to install mtroamd (see Installing mtroamd). If tmux is missing too, the banner offers only the install guide. After a confirmed "not installed", meshTerm keeps using tmux for that host for up to a day; after you install mtroamd, tap Check persistence on the host's Details to use it straight away.

"Connection Failed" on an mtRoam host

mtroamd is installed but meshTerm couldn't reach it. Tap Retry, or Open with tmux instead to open this one connection through tmux without changing the host's setting. Common causes: the daemon isn't running (check with mtroamd doctor, or systemctl --user status mtroamd), or, with the Direct transport, the firewall port isn't open (see Firewall setup under Choosing a transport, or switch to SSH Tunnel).

No Update, Repair or Uninstall button for mtroamd

Those buttons appear only for a copy meshTerm installed in ~/.local/bin. A copy from a package manager (or a source build) shows "Installed by a package manager." instead: update it with the package manager, for example sudo apt upgrade mtroamd. If meshTerm hasn't learned yet who installed the daemon, tap Check persistence on the host's Details first.

Package installed, but the old daemon is still running

The package's automatic migration didn't run for your user (for example you installed as root, or your user session wasn't reachable). Run /usr/bin/mtroamd migrate as your login user; see Switching to a package. Until then, package upgrades don't reach the running daemon.

"Connected via SSH Tunnel"

With the Direct transport, meshTerm couldn't reach the daemon's QUIC port, so it carried the session inside SSH instead. Sessions persist normally. To use Direct, open the daemon's port (see Firewall setup in Edit Host > Connection).

Tailscale

Tailnet device browser is empty or asks for a token

When meshTerm is connected to your tailnet (Built-in mode), the device list comes straight from the tailnet with no API token needed. A read-only API token is only needed to browse while you are not connected (offline, or a profile you haven't signed into). Add one under Settings → Hosts & Network → Tailscale if you want that. See the Tailscale Setup Guide.

"Invalid or expired token."

Tailscale API tokens expire. If you use one, generate a new one at login.tailscale.com and paste it into Settings → Hosts & Network → Tailscale.

Tailnet devices missing from the browser

  • Only authorised devices appear. Check your Tailnet's device-authorisation settings.
  • Confirm the API token was generated for the correct Tailnet.
  • Pull to refresh.

Security warnings

Host key mismatch

The server's host key has changed since you last connected. This can mean a legitimate change (server rebuilt, keys rotated) or something more suspicious. If you're confident the change is legitimate:

  1. Settings → Hosts & Network → Trusted servers.
  2. Find the entry and swipe to delete.
  3. Reconnect; you'll be asked to trust the new fingerprint.

If you're not sure, do not reconnect. Investigate the server directly first.

App Lock

"meshTerm requires a device passcode."

App Lock can't be enabled without a device passcode. Set one in iOS Settings → Face ID & Passcode, then return to meshTerm.

SFTP

"SFTP subsystem not available"

The server doesn't have the SFTP subsystem enabled. In OpenSSH, ensure /etc/ssh/sshd_config contains Subsystem sftp /usr/lib/openssh/sftp-server (the exact path varies by distro) and restart sshd.

Permission denied on rename / delete / mkdir

Your account needs write permission on the target directory. Some SFTP servers reject cross-filesystem renames - keep the target in the same directory.

Purchases

"Purchase could not be verified."

There was a problem verifying with the App Store.

  • Check your internet connection.
  • Try Restore Purchases in Settings.
  • If the issue persists, contact Apple Support via the App Store.

Ask in our GitHub Discussions, or report a bug from Settings > Feedback and Feature Requests. See Feedback and feature requests.
