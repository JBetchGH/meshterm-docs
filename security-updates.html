meshTerm 2.4 - Security updates
Know when a host has security fixes waiting, and install them in one step.

1. What meshTerm checks

When you connect to a host, meshTerm checks it for available security updates, at most once a day per host. The check uses the connection you already opened, or a brief SSH connection of its own for a host you reach only through Roam. It is read-only and needs no administrator rights: nothing is installed or changed on the host, and you don't need to do anything to turn it on.

meshTerm reports updates you can install, not whether a host is safe. It never calls a host "vulnerable": it tells you that a fix has been published for something installed there, and offers to install it.

Tailscale (free)

If Tailscale is installed on the host, meshTerm compares its version with a set of rules that meshTerm curates and publishes in its signed security feed. If the host's Tailscale has a security fix in a newer version, the host shows it.

Recommended updates aren't security fixes (for example a Tailscale SSH stall fix); some apply only when you reach the host over your tailnet. They're listed in the host's Security updates screen but not counted on the host row.

Installed packages (Pro)

With meshTerm Pro, meshTerm also compares the host's installed packages with known CVEs (published security issues) rated High or Critical, where the fix is already published in the host's own distribution repositories. A CVE that has no fix in those repositories yet is not shown, because there is nothing to install. Medium and Low issues are not shown.

The result counts packages with an update, not CVEs: one package update often fixes several CVEs at once, and installing it clears them all.

The kernel

  • A kernel fix that isn't installed yet counts straight away when Install Updates can install it: on Alpine, AlmaLinux, Rocky Linux and RHEL, and on Debian and Ubuntu when the kernel's meta package (such as linux-image-generic) is installed. Without that package, Install Updates can't bring in a newer kernel: the kernel row offers Open Terminal to install one with the system's own tools, and it counts only once the fix is more than 7 days old.
  • A kernel fix that is installed but waiting for a restart counts only once the fix is more than 7 days old. Most servers restart on their own schedule, so meshTerm doesn't ask for a restart the day a fix comes out.
  • When a live kernel patch is loaded (Ubuntu Livepatch, or kpatch on AlmaLinux, Rocky Linux and RHEL), the kernel row still shows, but it never counts on the host row's pill. On AlmaLinux, Rocky Linux and RHEL the row says "Live kernel patch loaded" and asks you to restart into the newer kernel when you can, because kpatch covers only selected CVEs; elsewhere it says "Covered by Livepatch until restart".

2. Where it shows

On the host row: a small shield pill, such as 3 updates, shows how many updates the host has waiting. There is no pill when there is nothing to install, when the host hasn't been checked yet, or when the security data is out of date (see What stays on your phone).

In Host Details > Security updates: the full list for the host.

  • One row per package, with the installed version → the fixed version, and Critical or High.
  • Under each package, the CVEs it fixes, each one linking to its entry in the distribution's security tracker (Ubuntu's, Debian's or Alpine's; for AlmaLinux, Rocky Linux and RHEL, Red Hat's CVE pages).
  • A kernel row, when a kernel fix is waiting to be installed or needs a restart, or a live kernel patch is covering it.
  • The Tailscale result, including any Recommended rows.
  • A footer, "Checked <time> against data from <date>", so you can see how recent the check and the data are.

From this screen you can install the updates, restart the server when it needs it, or check again.

4. What stays on your phone

The comparison happens on your iPhone or iPad, and the package list stays there. What the downloads tell GitHub, which hosts meshTerm's security data, is which releases your servers run.

  • The security data: the phone downloads meshTerm's signed security feed from its public site on GitHub Pages. The feed is a small manifest, fetched when you open the app at most once every 12 hours (sooner only to retry a download that failed, or when you tap Check Again on out-of-date data), plus, with Pro, one data file per release your hosts run, such as debian-12. For an Ubuntu release that has an Ubuntu Pro (ESM) fix list, the phone downloads that list too, whether or not the host has Ubuntu Pro attached, so GitHub can't tell which hosts have it; it is used only for hosts that do. GitHub sees these requests and your phone's IP address, so it learns which releases your servers run: for example, that this IP address has a Debian 12 host. It doesn't learn the hosts' names, addresses or packages. The requests carry no cookies, account or identifier.
  • The package list (Pro): meshTerm reads the host's installed packages with the read-only check, which needs no root and installs nothing. The list is compared with the feed on the device and never leaves it: it isn't sent to anyone, synced to iCloud or included in device backups. Deleting the host, or Erase This Device in Settings, removes it. Without Pro, a host's packages are never read.
  • The feed carries data, not commands. It is signed, and meshTerm ignores it unless the signature checks out. The commands meshTerm offers to run come from elsewhere (see Installing updates).
  • Old data is not used. If the security data on the phone is more than 7 days old, for example because the phone couldn't download a newer feed, meshTerm shows "Security data is out of date" with Check Again, instead of results that may be wrong.

See also the Privacy Policy.

5. Installing updates

Install Updates runs the update for you in a terminal tab on the host, so you can watch it and answer any prompt. The screen shows the exact command, and nothing runs until you tap Install Updates. Copy Command copies it instead, if you'd rather run it yourself.

The command comes from meshTerm's signed host recipes (the same signed set of commands meshTerm uses for other setup steps), not from the security feed, and it names only packages that are installed on the host. It upgrades those packages, from the host's own repositories. An upgrade can also install new packages that they now need, such as a newer kernel or a new dependency:

SystemCommand
Debian, Ubuntusudo apt-get update && sudo apt-get install --only-upgrade -y <packages>
Alpinesudo apk -U upgrade <packages>
AlmaLinux, Rocky Linux, RHELsudo dnf --refresh upgrade -y <packages>
  • When you sign in as root, the command runs without sudo.
  • Only on a host that has no sudo at all does the command run through su instead: the screen says "It asks for the root password.", and the terminal asks for it.
  • When the host has sudo but your account isn't in one of its administrator groups (such as sudo, wheel or admin), the command still uses sudo, since some servers grant it by name, and the screen adds "If your account can't use sudo, ask the server's admin to run this."
  • A package whose name is too long to include in the command is left out of it, and the screen says how many, for example "2 packages need updating by hand, in a terminal." Update those with the system's own tools.
  • Installing updates never restarts the server. If a fix needs a restart, Restart Server appears separately.
  • When the command finishes, meshTerm checks the host again and updates the list.
Rocky Linux and RHEL EUS

Rocky Linux and RHEL hosts are checked against Red Hat's fixes, so on them the screen adds "Some fixes may not be available from your vendor yet."

  • Rocky Linux publishes Red Hat's fixes some time after Red Hat does. Until then the update installs nothing for that package, and the row clears at the next check after Rocky ships the fix.
  • RHEL with Extended Update Support (EUS): the host is matched against RHEL's main repositories, not the EUS ones, so it keeps showing the row until it leaves EUS.

6. Restarting the server

Restart Server is a separate button, offered only on Linux servers (never on macOS, Windows or a system meshTerm doesn't know). It appears only when a newer kernel with the fix is installed but not running yet, or when the host itself reports that it needs a restart.

  • meshTerm asks first: "Restart this server? Every session and program on it ends, including tmux and mtRoam sessions, and anyone connected is disconnected. meshTerm checks it again when you reconnect." Save your work first.
  • It runs systemctl reboot, or shutdown -r now where that isn't available, and reboot on Alpine, with sudo (or su) as for Install Updates.
  • When you reconnect, meshTerm checks the host again.

7. Updating Tailscale

For Tailscale, meshTerm shows the update command to copy, with Open Terminal to run it on the host yourself.

Updating Tailscale can drop your connection

Updating Tailscale restarts it, which can drop connections that go through your tailnet, including the one you are using to run the update. Reconnect afterwards, and meshTerm checks the host again.

  • macOS, Tailscale from the App Store: update it from the App Store on the Mac.
  • Windows: update from Tailscale's menu in the system tray, or run tailscale update in PowerShell as an administrator.

8. End of life and Ubuntu Pro

End of life: meshTerm's signed security data carries the date each release stops getting security fixes from its distribution. When a host's release is past that date (for example Debian 11, or Ubuntu 20.04 without Ubuntu Pro), meshTerm shows "This release no longer gets security fixes" beside its results. Fixes published before then still show, but new issues won't be fixed on that release, so they can't show up as updates: upgrading to a supported release is the way to keep getting fixes. A release the data gives no date for never shows the note, and Ubuntu 20.04 with Ubuntu Pro attached is not past its end of life.

Ubuntu Pro (ESM): some Ubuntu fixes are published only through Ubuntu Pro's Expanded Security Maintenance. meshTerm shows those fixes only on hosts that have Ubuntu Pro attached, because other hosts can't install them. With Pro, the phone downloads the Ubuntu Pro fix list for every Ubuntu release that has one, whether or not the host has Ubuntu Pro attached, so the download doesn't tell GitHub which hosts have it.

9. Supported systems

CheckSystems
Installed packages (Pro)Ubuntu 20.04, 22.04, 24.04, 26.04 and 26.10; Debian 11, 12 and 13; Alpine 3.20 to 3.24; AlmaLinux 8 to 10; RHEL 8 to 10; Rocky Linux 8 to 10 (checked against Red Hat's data)
TailscaleEvery host with Tailscale installed, including Windows and macOS

Not yet supported for the package check: Fedora, CentOS Stream, Oracle Linux, Amazon Linux, Arch, SUSE, Linux Mint and the 32-bit Raspberry Pi OS. On these, Pro shows "Package check isn't available for <system> yet". The Tailscale check still works on them.

Not covered on any system:

  • Language packages, such as pip, npm, gem or cargo packages.
  • Snaps and Flatpaks.
  • Containers and their images (see Containers for the containers themselves).
  • Software installed outside the package manager, such as from a downloaded file or built from source.

10. Checking again

meshTerm checks each host at most once a day on its own. Check Again in Security updates checks now, over the open connection. If the host isn't connected, the check runs the next time you connect to it. When the security data is out of date, Check Again also downloads newer data.
